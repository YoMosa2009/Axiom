# Axiom versioning policy

Axiom uses Semantic Versioning in `MAJOR.MINOR.PATCH` form.

- `MAJOR`: incompatible product, data, configuration, or update-system changes
- `MINOR`: backward-compatible features or substantial capability additions
- `PATCH`: backward-compatible bug fixes, reliability work, and small polish

The version in `Malx_AI/Malx_AI.csproj` is the source of truth. Every shipped
build must use the same version in all user-visible and release surfaces.

## Version locations

For every release, update and verify:

1. `Malx_AI/Malx_AI.csproj` — `<Version>`; authoritative executable/package version
2. `Malx_AI/MainWindow.xaml` — Settings version label
3. `CHANGELOG.md` — dated release entry
4. `README.md` — current release badge
5. Git tag — lowercase `vMAJOR.MINOR.PATCH`, exactly matching the project version
6. Release ZIP and `AXIOM_UPDATE_MANIFEST.txt` — generated by the clean publish script

Do not replace historical statements such as “V1.7.0 and newer” when they describe
the minimum version that introduced a feature. Do not change unrelated dependency
versions that happen to contain the same number.

## Release decision

Before changing the version, compare against the last shipped version:

- Fix only: increment `PATCH` (`1.7.0` → `1.7.1`)
- Backward-compatible feature: increment `MINOR` and reset patch (`1.7.1` → `1.8.0`)
- Breaking change: increment `MAJOR` and reset minor/patch (`1.8.0` → `2.0.0`)

Pre-release builds, if used, must follow SemVer suffixes such as `1.8.0-beta.1` and
must be published as GitHub prereleases. Axiom's stable updater ignores prereleases.

## Required release check

1. Run unit tests and a Release build.
2. Run `scripts/Publish-GitHubRelease.ps1 -PackageOnly` for a local release candidate.
3. Smoke-test the generated folder, including cloud/local startup and update checks.
4. Confirm the executable version, Settings label, changelog, tag, manifest, and ZIP
   all identify the same version.
5. From a clean, synchronized `main`, run `scripts/Publish-GitHubRelease.ps1` to publish
   a non-draft GitHub Release and upload the generated ZIP unchanged.

See `RELEASING.md` for the packaging and GitHub Release procedure.
